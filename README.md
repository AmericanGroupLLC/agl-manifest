# agl-manifest

Delivery and status for all **42 American Group LLC mobile apps**, from one
place.

**[STATUS.md](STATUS.md)** is the whole portfolio in one file: every app, its
package name, what it supports, its AdMob ids, its App Store record, the files
it still needs, and every credential still to be created. The same data as a
spreadsheet is [`status.csv`](status.csv) — one row per app, 25 columns.

Both are generated by `python3 scripts/status.py`, which asks GitHub and App
Store Connect what is actually there rather than repeating what someone wrote
down.

Each row carries the **package name and bundle id**, because that is the string
AdMob, Play Console, App Store Connect and `keytool` all ask for — so the tables
are the thing to work from when creating AdMob apps, upload keys or store
records.

## Where the portfolio stands

| | Count |
| --- | ---: |
| Mobile apps in the org | 42 |
| Flutter, buildable today | 36 |
| Not ported yet | 6 |
| Apps with a signed Android binary you can download and install | 36 |
| Apps with a verified signed `.aab` and `.apk` built | 37 of 37 |
| Apps whose **iOS** delivery is blocked on a signing certificate | 37 |
| App Store Connect records that already exist | 40 (29 matching a live bundle id) |

Every Android artefact has had its signing certificate compared against the
upload keystore it was meant to use, and the fingerprint is published with it —
so the claim is checkable with `apksigner verify --print-certs` rather than
taken on trust. Section 2 of [STATUS.md](STATUS.md) lists them.

Nothing iOS has been built or verified yet. Treat the iOS columns as structural
(the plist keys and privacy manifests are in place), not as evidence that an
`.ipa` compiles — see [`docs/KNOWN_ISSUES.md`](docs/KNOWN_ISSUES.md).

One app, **Kinnav**, has been transferred out to `srpatcha/Kinnav` and is
reachable only through a GitHub redirect. It is still delivered by this
manifest; if that redirect is removed, delivery for it stops.

## Why this repository exists

37 Flutter apps in 37 repositories, each running its own CI on every push — a
runner boot, a Flutter SDK download, a cold pub cache, an Android build and a
macOS iOS build. Identical work every time, and the macOS half bills at **10×**.

This does the same work once for the batch.

```
apps.json                  generated from the backend's measured audit
fastlane/Fastfile          the batch lanes
scripts/checkout.py        shallow-clones the selected apps into work/
scripts/status.py          regenerates STATUS.md and status.csv
scripts/appstore_records.rb  asks App Store Connect which records exist
.github/workflows/
  validate.yml             analyze + test + iOS build, whole portfolio, nightly
  deliver.yml              manual: TestFlight / Play, per platform and lane
  artifacts.yml            installable builds attached to each app's Releases
  status.yml               refreshes the tables nightly and after a delivery
  sync-manifest.yml        notices when apps.json stops matching the org
```

### What runs where

| | Where | When | Cost |
| --- | --- | --- | --- |
| Analyze + release sanity checks | the app repo | every pull request | ~2 min, ubuntu |
| Full test suite, all apps | here | nightly, or on demand | one ubuntu job |
| iOS build, all apps | here | nightly, after tests pass | one macOS job |
| TestFlight / Play | here | manual dispatch | one job per delivery |
| Installable APK / simulator build | here | weekly, or on demand | one job |

The app repos deliberately have **no `push` trigger**. Pushing to a default
branch is covered by the nightly batch.

### Where the saving comes from

Not from doing less work — the analyzing and testing is the same wherever it
happens. From not paying the fixed costs 37 times:

- one runner boot instead of 37
- one Flutter SDK download instead of 37
- one warm pub cache instead of 37 cold ones
- one CocoaPods spec fetch instead of 37 — every app pulls the same Firebase
  and AdMob pods
- **one macOS runner instead of 37**, which is the whole game at 10× billing

## Running it

```sh
bundle install

# Everything, or a slice: all | android-deliverable | ios-deliverable | ads | Name,Name
bundle exec fastlane validate apps:all
bundle exec fastlane build_all platform:ios apps:CalcMaster,MyHealth

# Each app's own lanes, run across the batch
bundle exec fastlane batch platform:android lane:beta apps:all
bundle exec fastlane batch platform:ios lane:release apps:TripNest

# Installable builds attached to each app's GitHub Releases
bundle exec fastlane publish_artifacts platform:android apps:all

# Refresh the tables
python3 scripts/status.py
```

Each app keeps its own `Fastfile` — flavours, export options, the dSYM upload,
an IPA existence check. This does not replace any of that. It checks the apps
out and runs their lanes with `BUNDLE_GEMFILE` pointing back here, so fastlane
is installed once for the batch instead of 37 times.

One bad app never stops the batch. Failures are collected and reported together
at the end, so a single run tells you everything that is broken rather than the
first thing.

## apps.json is generated, not written

```sh
python3 scripts/audit_release_readiness.py
python3 scripts/generate_manifest.py --out apps.json
```

The audit measures the repositories — where each Flutter project actually lives,
its application id, whether it has a real signing config, which auth providers
it declares. A new app, a moved project directory or a renamed bundle id reaches
delivery by re-running that, not by someone editing a list. `sync-manifest.yml`
fails if `apps.json` and the org drift apart.

Once generated, this repository stands alone: `apps.json` is committed, and
every table is built from it plus live GitHub queries. Nothing here reads the
private backend at runtime.

## Secrets

One organization secret does most of the work:

| Secret | Why |
| --- | --- |
| `AGL_PACKAGES_TOKEN` | Clones the app repos, and lets `flutter pub get` reach the shared Flutter packages. Without it every job dies with `could not read Username for 'https://github.com'`. Needs **write** access as well to publish release binaries. |

Delivery additionally needs the store credentials, all env-driven and never in
the repository — see [STATUS.md](STATUS.md) §4 and §5.

The `release` lane runs in the `production` GitHub environment. Add required
reviewers under **Settings → Environments → production** and anything
store-facing waits for a human. `beta` does not.
