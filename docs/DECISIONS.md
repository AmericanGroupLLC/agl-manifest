# Decisions

Why the ecosystem is built the way it is. Each entry records what was decided,
what it cost, and what would justify revisiting it — so a later session can
disagree on evidence rather than rediscover the argument.

---

### ADR-001 — `agl-manifest` is the only repository that runs CI

**Decided** 2026-09. **Status** in force.

37 Flutter repositories each running their own workflow meant 37 runner boots,
37 Flutter SDK downloads and 37 cold pub caches for what is the same validation.
The macOS half of that bills at **10×** the Linux rate.

Actions are disabled in the app repositories; `agl-manifest` validates and
delivers them centrally.

*Cost:* a push to an app repo gets no immediate feedback — the manifest's
scheduled run finds it. *Revisit if* per-repo feedback latency starts causing
broken merges.

---

### ADR-002 — Status files are measured, never maintained

**Status** in force.

`STATUS.md`, `status.csv`, `apps.json`, `docs/release-readiness.json` and
`docs/build-evidence.json` are all generated by scripts that inspect the repos,
GitHub and App Store Connect. Hand-editing any of them is forbidden.

A hand-maintained status table is wrong within a week and then actively
misleads, because it looks authoritative. `scripts/status.py` refuses to run
without a working `GH_TOKEN` rather than emit a table of empty columns that
would read as "no app has a release".

### ADR-003 — Shared behaviour lives in `packages/`, not copied into 37 apps

**Status** in force.

`agl_i18n`, `agl_observability` and `agl_ads` are consumed as git dependencies.
One fix reaches every app.

*Cost:* CI cannot resolve a private git dependency without a token, so the whole
portfolio's CI is blocked on one secret (`MANUAL_ACTIONS.md` MA-002). That is a
real and known downside of this choice.

### ADR-004 — Android release bundles are built locally, not in CI

**Decided** 2026-09-11. **Status** in force.

Android does not need a macOS runner, and building locally produces uploadable
artefacts *before* the CI credentials exist. `scripts/build_release.py` does it.

*Revisit when* MA-002 is resolved and CI can build unattended.

---

### ADR-005 — Every bundle's signature is verified against its keystore

**Decided** 2026-09-11. **Status** in force.

A release build whose `signingConfig` is misconfigured does not fail. It falls
back to the debug key and produces a valid-looking `.aab` that Play rejects at
upload — the most expensive place to discover it.

So `build_release.py` extracts the signing certificate from each bundle and
compares its SHA-256 against the upload keystore's, and reports
`SIGNATURE_MISMATCH` on any difference. A build is not "done" because Gradle
exited 0.

### ADR-006 — Machine-specific build workarounds stay out of the app repos

**Decided** 2026-09-11. **Status** in force.

This build machine denies the JVM's IPv6 `connect()` and blocks direct egress.
Both were briefly worked around by editing `android/gradle.properties` in all 37
apps; that was **reverted**, because none of it is true of the applications — it
is true of one machine, and it would have been committed as though it were a
property of the software.

The flags are supplied through `JAVA_TOOL_OPTIONS` by the build script instead,
which also has the advantage of reaching the Gradle daemon (a project's
`org.gradle.jvmargs` did not).

### ADR-007 — Accessibility labels are only added where the meaning is certain

**Decided** 2026-09. **Status** in force.

231 of 447 `IconButton`s had no `tooltip`, so a screen reader announced them as
"button" and nothing else. 215 were labelled; **16 were deliberately left
unlabelled** (`chevron_right`, `swap_horiz`, `replay_30`, `north_west`, …)
because their meaning depends on context.

A wrong label is worse than no label: "button" tells a user nothing, but
"Delete" on a control that shares actively misleads.

`tooltip` was used rather than a `Semantics` wrapper because Flutter already
feeds it to the semantics tree, and it doubles as a long-press label on Android.

### ADR-008 — A claim of completion requires the output that proves it

**Status** in force.

Analyzer, test, build and upload results are only reported when the command was
actually run in that session and its output seen. This exists because green
`flutter analyze` and green tests once coexisted with an app that opened to a
white screen — passing gates are evidence about the gates, not about the app.

Corollary: a metric that does not measure what it claims gets fixed rather than
reported. The accessibility metric counted only `Semantics()` and
`semanticLabel`, so it read "21 apps with zero named controls" *after* 215
tooltips were added. Counting `tooltip:` — which is what a screen reader
actually announces — the true figure was 4.

---

### ADR-009 — Formatting is not run as part of unrelated changes

**Status** in force.

These repositories do not enforce formatting. A `dart format` pass bundled into
an accessibility change rewrote whole files and buried 216 real edits under
**5,048 lines** of churn, making the change impossible to review. It was
reverted and redone without it.

---

### ADR-010 — Bundle ids and package names are treated as permanent

**Status** in force.

Once a store record exists, the identifier cannot be changed — a rename means a
new app, losing reviews and installs. `docs/APP_IDENTIFIERS.md` is the reference
and must be checked before any repo or product rename.

This is why the `ratiotune` → `radiotune` typo was fixed *before* a store record
existed, and why 13 apps without records and 11 orphaned records are recorded as
a decision to make rather than silently reconciled.
