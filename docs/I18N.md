# Localization across the portfolio

One library, `packages/agl_i18n`, is the localization for all 43 mobile apps.
Its own README is the reference for using it. This file records **what is
actually translated**, measured, and what to do about it.

The table below is generated. Re-run it rather than editing it:

```bash
python3 scripts/audit_i18n.py --print       # -> docs/i18n-audit.json
python3 scripts/audit_i18n.py --markdown    # -> the table in this file
```

Measured 2026-09-13 against the local mirror at `/Users/spatchava/agl`.

## The headline

**Six of forty-three apps are genuinely translated.** Twenty-three have the
locale machinery installed and not one screen reading it.

| Verdict | Apps | What it means |
| --- | ---: | --- |
| **real** | 6 | The UI reads localized strings and the device picks the language |
| partial | 4 | Some screens translated, most not |
| **PINNED** | 5 | Translated, but the phone's language is ignored |
| shell | 23 | Locales declared, delegates installed, **zero** screens read a string |
| none | 5 | No localization of any kind |

Across the portfolio, **244 of 996 widget-building files read a localized
string**, and 7,367 user-visible string literals are still hardcoded in Dart.

The number that matters for a release is not "does the app have twelve
locales". Every measurement below exists because that number was 12 for
thirty-three apps and told us nothing.

## What is measured, and why each column exists

| Column | Measurement | Why |
| --- | --- | --- |
| `agl_i18n` | `agl_i18n` in `pubspec.yaml` | Cheapest possible signal, and the one that misleads |
| `l10n.yaml` | the app has its own `gen-l10n` config | Distinguishes "uses the shared 66 strings" from "has its own catalogue" |
| locales | `MaterialApp.supportedLocales`, resolved through identifiers, `AglLocales.standard`, `AglLocaleController` and list comprehensions | What the binary claims at runtime |
| iOS | `CFBundleLocalizations` entries in `Info.plist` | **This is the list the App Store product page displays as "Languages".** It is the store listing, in the binary |
| Android | `resConfigs` / `resourceConfigurations` | Resources outside this list are stripped from the AAB — a locale not here cannot work on Android whatever Dart says |
| l10n calls | `l10n.`, `AppLocalizations.of(`, `AglL10n.of(`, plus each app's own alias getter | Reading a string is the only thing that translates a screen |
| UI files reading l10n | files with `Widget build(BuildContext)` that read a localized string, over all such files | Reach. A high call count concentrated in one screen is not a translated app |
| hardcoded copy | string literals in `Text(...)`, `hintText:`, `tooltip:`, `title:` and similar, excluding asset paths, route names, format patterns and pure interpolations | The size of the remaining job |
| `MaterialApp.locale` | resolved to the class that owns it, then to that member's nullability and initial value | `null` means the device decides. Anything else can silently override it |

Three narrower claims that are also false:

- **FashionFactory and TripNest set `resourceConfigurations += listOf("en")`.**
  Their Android builds strip every non-English resource, so even Material's own
  widgets stay English no matter what the device is set to, while `Info.plist`
  promises twelve. The two files disagree inside one product.
- **Kinnav under-claims.** 170 call sites and 25 of 29 UI files translated, and
  `Info.plist` lists six languages against twelve in Dart. The App Store would
  show six for an app entitled to claim twelve.
- **Four of the six genuinely translated apps advertise no languages at all.**
  AGCleaner, AGRecorder, MileMaster and WiFiTrail have no
  `CFBundleLocalizations` and no `resConfigs`. The work is done and the store
  will not say so.

The honest short-term fix for the twenty-four is not translation. It is to cut
`CFBundleLocalizations` and `resourceConfigurations` back to the languages the
app actually renders — one language, in most cases — and restore them as each
app is translated. That is a one-line change per app and it makes every listing
true the same day.

## The three ways an app fails while looking fine

### 1. Delegates installed, nothing reads them (23 apps)

The common shape. `pubspec.yaml` has `agl_i18n`, `MaterialApp` has
`aglLocalizationsDelegates(...)` and `AglLocales.standard`, `Info.plist` has
twelve entries — and `grep` finds no call site anywhere in `lib/`. What the
device language actually changes is Material's own strings: the date picker,
"OK", the text-selection menu. Everything the app itself wrote stays English.

Worst case by size: **Photriya**, 64 widget-building files, 900 hardcoded
strings, zero call sites.

Most misleading: **MyFinance** carries a 25-language translation table at
`lib/i18n/translations.dart` — 2,135 lines — that **no file imports**. Verified
by grep: outside the file itself, the only i18n reference in `lib/` is
`import 'package:agl_i18n/agl_i18n.dart'` in `main.dart`.

**Verba** is the same story with a complete hand-written twelve-language
`AppLocalizations` at `lib/core/i18n/app_localizations.dart`. The only two
references to it in the whole app are `AppLocalizations.delegate` and
`AppLocalizations.supportedLocales`, both on `MaterialApp`. Not one of its 28
UI files calls `AppLocalizations.of(context)`.

**Five apps ship a working language picker that changes nothing** the app
wrote: HomeWise, NearServe, portfolio-board, RideZap and yourtube all construct
a picker and have zero call sites. A user can select Japanese and watch the
screen stay in English.

### 2. `MaterialApp.locale` overrides the device (2 apps)

- **DriftDate** — `LocaleController.locale` is a **non-nullable** `Locale`
  getter over `String _localeCode = 'en'`. A non-null `Locale` always reaches
  `MaterialApp`, so the phone's language is never consulted. 20 of 37 UI files
  read its 11-language table, and every one of them opens in English.
- **iMeasure** — `locale: Locale(prefs.language)` with
  `String _language = 'en'` in `PreferencesService`. Sixteen languages, all
  unreachable until the user finds the setting.

### 3. The app's copy is keyed off a private preference that starts at English (3 apps)

Subtler, and the reason this audit has a fourth verdict. **MyHealth**,
**Uscis-Case** and **VirtuBand** leave `MaterialApp.locale` null — correctly —
so Material's widgets do follow the device. But their own strings come from a
separate `language` field that is initialised to `'en'` and, verified by grep,
is never seeded from the platform: none of the three references
`platformDispatcher.locale`, `Platform.localeName` or `window.locale`.

On a Spanish phone the result is a Spanish date picker inside an English app.
`MyHealth` is the sharpest case: 111 of 144 UI files read its table, the table
has **three** languages, and `Info.plist`, `resConfigs` and `supportedLocales`
all say twelve.

## Ranked adoption plan

Ordered by damage per unit of work, not by app size.

### Tier 0 — make the listings true (this week, before any submission)

Nothing here is translation work.

1. **Cut `CFBundleLocalizations` and `resourceConfigurations` to the languages
   each app actually renders** in the 24 apps listed above. One line each.
2. **Add them to AGCleaner, AGRecorder, MileMaster and WiFiTrail**, and widen
   Kinnav's from 6 to 12. These four apps earned the claim and are not making
   it.
3. **Reconcile FashionFactory and TripNest**, whose iOS and Android
   declarations contradict each other within one product.
4. Wire the check into `scripts/audit_i18n.py` in CI so
   `ios_cfbundle_localizations > 1 and grade in (shell, pinned, none)` fails the
   build. The gap reopens silently otherwise.

### Tier 1 — fix the apps that are translated and do not show it (2–3 days)

Highest return in the portfolio: the strings already exist.

| App | Change |
| --- | --- |
| DriftDate | Make `LocaleController.locale` return `Locale?` and start `_localeCode` null. 20 files light up at once |
| iMeasure | `locale: prefs.language == null ? null : Locale(prefs.language!)`; default the pref to null |
| MyHealth | Seed `_language` from `platformDispatcher.locale` when nothing is stored — then grow the table past en/es/fr, or cut the declared set to three |
| Uscis-Case | Same seed; its table already has 9 languages |
| VirtuBand | Same seed; its table already has 13 languages |

Each needs a widget test at `localesTestValue` = a non-English locale asserting
a translated string renders. Without that the fix regresses invisibly.

### Tier 2 — finish the four partial apps (1–2 weeks)

CalcMaster (18/40), iMaps (15/39), daily-pulse (8/28), NexusTransferPay
(13/17). The plumbing is right and the pattern is established; this is
per-screen work with a known finish line. Do the first-run screens first —
onboarding, splash, auth — because those decide whether the app *looks*
translated.

### Tier 3 — the 23 shells

Do not do these in size order. Do them in this order:

1. **Trivial (one UI file each): RoomCraft, MyFinance, ChefCount.** 30–56
   strings. Each is an afternoon and each converts a lie into a truth.
2. **Small and self-contained: AGrammarly (42), portfolio-board (103), RideZap
   (105), FashionFactory (108), GadgetNest (112), NearServe (114), NewsBoard
   (122), CarDeal (145), HomeWise (151).** Prioritise the five with a live
   picker (HomeWise, NearServe, portfolio-board, RideZap, yourtube) — those
   promise the user a control that does nothing.
3. **Large: radiotune (174), yourtube (217), HerJourney (214), TripNest (233),
   BodyQuest (234), Verba (319), EventSpark (434), GroceryMatch (611),
   PilotEnRoute (665), Photriya (900).** Plan these as real work. Photriya and
   PilotEnRoute together are 1,565 strings.
4. **Verba and GroceryMatch need a decision before the work**, not during it:
   Verba has a complete 12-language catalogue to wire up rather than write, and
   GroceryMatch has a 6-language Dining table to either extend to 12 or fold
   into the shared ARB.
5. **CodeDeal** declares 19 locales through its own `l10n.yaml` and reads none
   of them; reconcile with the standard 12 before adding call sites.

### Tier 4 — the five with nothing

AeroSwift, ApexMarketWatch, BuddyPlay, MyCard, PlantPulse have no
`supportedLocales` at all. They are also the apps mid-rebuild. Adopt the
library as part of the rebuild rather than as a separate pass, and do not let
them reach a store record with a multi-language listing first.

## The standard set

`en, es, zh, hi, fr, ar, de, ja, pt, ko, it, ru`

Twelve, matching what CalcMaster had already declared — the only explicit list
in the portfolio when this started. Chosen for the largest App Store and Play
markets, and to include a right-to-left script: Arabic ships in every app, so
RTL layout bugs surface in development rather than in review.

Apps that already shipped more keep them. `AglLocaleController(extraLocales:)`
adds to the standard set and never removes from it, so iMaps keeps Turkish,
Indonesian and Swahili and NexusTransferPay keeps its 25.

## The decision, and why the library exists

Every app that had any i18n had invented its own. The languages shipped were 3,
6, 9, 11, 12, 13, 15, 16 and 25 depending on which app you opened, and the
`Apps` sheet of the planning workbook recorded `i18n: Yes` for nearly all of
them, which was not accurate. Three consequences that matter for a store
release:

1. **A listing can promise a language the binary does not contain.** Still true
   for 24 apps; see above.
2. **The same word was translated repeatedly, and inconsistently.** "Cancel"
   appeared in 18 apps.
3. **Adding a language meant editing 42 repositories.**

So the languages, the locale controller, the picker and the shared vocabulary
live in one package, and each app owns only the strings that are actually its
own.

## What migrating an app involves

1. `agl_adopt.py <repo> <strings.json>` — dependency, `l10n.yaml`, ARB files.
2. Wire `MaterialApp`: `locale`, `supportedLocales`,
   `aglLocalizationsDelegates(AppLocalizations.delegate)`.
3. Replace call sites; delete the app's own locale plumbing.
4. `flutter gen-l10n`, then `analyze` and `test`.
5. Bring `CFBundleLocalizations` and `resourceConfigurations` up to match —
   only once step 3 is done.

Step 2 is deliberately manual. The root widgets differ too much — Riverpod,
provider, bare `setState`, `MaterialApp` versus `MaterialApp.router` — and a
regex that rewrites all of them is a regex that breaks some of them silently.

Steps 1–2 are what "adopted the library" meant for the 24 apps counted as
adopted on 2026-09-10. Step 3 is the one that translates an app, and for those
24 it has not happened.

## Things worth knowing before doing the next one

- **Count call sites, not ARB keys.** daily-pulse had 106 keys in nine
  languages and looked thoroughly localized. Only 6 of its 22 screens read a
  single one of them, and the onboarding screen — the first thing anyone sees —
  read none, so it opened in English no matter what the phone was set to.
- **`MaterialApp.locale` must be null to follow the device.** Several apps
  initialise their locale state to `Locale('en')`, which pins the app to
  English and makes the device's language irrelevant. Start at null and only
  set it when the user picks. A **non-nullable** `Locale` getter has the same
  effect and is harder to see — that is DriftDate's bug.
- **A null `MaterialApp.locale` is not sufficient if the copy comes from
  somewhere else.** If the app's strings are keyed off its own `language`
  preference, that preference must be seeded from `platformDispatcher.locale`
  on first launch, or the app is pinned to English while Material is not.
- **Tests need `SharedPreferences.setMockInitialValues({})`.** Without it the
  controller's `await` never returns and the test *hangs* rather than failing.
- **A generated delegate throws on an unsupported locale.** Fallback happens at
  `MaterialApp` level, so test resolution through the widget tree, or assert on
  `delegate.isSupported`.
- **In tests, set `localesTestValue`, not `localeTestValue`.** `WidgetsApp`
  resolves against `platformDispatcher.locales`; setting only the singular
  leaves the test running in English and passing for the wrong reason.
- **`intl` pinned to any exact-ish version will not resolve.** Eighteen apps
  pinned `intl: ^0.19.0` or `^0.20.2`; `flutter_localizations` depends on one
  exact `intl`, so any app constraint that excludes it makes the whole app
  unresolvable the moment localization is added. `intl: any` defers to the SDK,
  which is the only thing that actually decides.
- **Dropping a `const`** is usually needed on the parent widget once a child
  reads a localized string.
- **Translating a screen finds its layout bugs.** Localizing daily-pulse's
  onboarding surfaced two overflows immediately: a column with no scroll, and a
  text column that was not `Expanded` — the Russian subtitle ran 77px past the
  row. Neither showed in English. Screenshot at least one long language
  (Russian or German) and run a 320dp widget test after localizing a screen.
- **Do not hand-roll a `Directionality` wrapper.** `GlobalWidgetsLocalizations`
  already gives the resolved locale its own direction. A wrapper computed from
  app state overrides that, one frame behind.
- **Do not invent a different word to satisfy the repeated-English check.**
  French really does say "Scanner", Italian says "Password", German says
  "Version". Add the pair to that app's per-locale exemption list instead.

## Limits of this measurement

Stated so the numbers are not over-read.

- **`hardcoded copy` is a heuristic with a known error bar.** It counts
  literals in a whitelist of user-visible parameters and drops asset paths,
  route names, format patterns, `SCREAMING_CASE`, and strings that are only
  interpolation. It still counts a few non-copy literals (`'A+'` in WiFiTrail)
  and misses copy passed through a variable or a custom widget parameter not on
  the list. Treat it as the order of magnitude of the remaining job, not an
  exact backlog.
- **`UI files reading l10n` counts a file as localized if it reads one string.**
  A file with thirty strings and one call site counts as localized. The ratio
  is therefore an optimistic upper bound on reach.
- **Nothing here was run.** These are static measurements of source in the
  local mirror. No app was launched on a non-English device to confirm the
  behaviour, and that is the check that would make each verdict conclusive —
  see `build-it-and-look-at-it`. The five Tier 1 verdicts were each read by
  hand in the source as well as measured.
- **Translation quality is not measured at all.** An ARB entry that is English
  text under a Spanish key counts here exactly like a real translation.
