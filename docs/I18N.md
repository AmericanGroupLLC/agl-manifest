# Localization across the portfolio

One library, `packages/agl_i18n`, is the localization for all 42 mobile apps.
Its own README is the reference for using it; this file records the state of the
rollout and the decisions behind it.

## The decision

Every app that had any i18n had invented its own. Measured across the 42 repos
before this work started:

| Mechanism | Apps |
| --- | --- |
| Flutter `gen-l10n` with ARB files | 5 |
| A hand-rolled `Map<String, ...>` in Dart | 10 |
| None at all | 21 |
| Not a Flutter app yet | 6 |

The languages shipped were 3, 6, 9, 11, 12, 13, 15, 16 and 25 depending on which
app you opened. The `Apps` sheet of the planning workbook recorded `i18n: Yes`
for nearly all of them, which was not accurate.

Three consequences that matter for a store release:

1. **A listing can promise a language the binary does not contain.** Store
   metadata is authored per language; nothing tied it to what shipped.
2. **The same word was translated repeatedly, and inconsistently.** "Cancel"
   appeared in 18 apps.
3. **Adding a language meant editing 42 repositories.**

So the languages, the locale controller, the picker and the shared vocabulary
live in one package, and each app owns only the strings that are actually its
own.

## The standard set

`en, es, zh, hi, fr, ar, de, ja, pt, ko, it, ru`

Twelve, matching what CalcMaster had already declared — the only explicit list
in the portfolio. Chosen for the largest App Store and Play markets, and to
include a right-to-left script: Arabic ships in every app, so RTL layout bugs
surface in development rather than in review.

Apps that already shipped more keep them. `AglLocaleController(extraLocales:)`
adds to the standard set and never removes from it, so iMaps keeps Turkish,
Indonesian and Swahili.

## What migrating an app involves

1. `agl_adopt.py <repo> <strings.json>` — dependency, `l10n.yaml`, ARB files.
2. Wire `MaterialApp`: `locale`, `supportedLocales`,
   `aglLocalizationsDelegates(AppLocalizations.delegate)`.
3. Replace call sites; delete the app's own locale plumbing.
4. `flutter gen-l10n`, then `analyze` and `test`.

Step 2 is deliberately manual. The root widgets differ too much — Riverpod,
provider, bare `setState`, `MaterialApp` versus `MaterialApp.router` — and a
regex that rewrites all of them is a regex that breaks some of them silently.

## Things worth knowing before doing the next one

- **Tests need `SharedPreferences.setMockInitialValues({})`.** Without it the
  controller's `await` never returns and the test *hangs* rather than failing.
- **A generated delegate throws on an unsupported locale.** Fallback happens at
  `MaterialApp` level, so test resolution through the widget tree, or assert on
  `delegate.isSupported`.
- **`intl` pinned to `^0.19.0` will not resolve** alongside
  `flutter_localizations`. Use `any`.
- **Dropping a `const`** is usually needed on the parent widget once a child
  reads a localized string.
- **`intl` pinned to any exact-ish version will not resolve.** Eighteen apps
  pinned `intl: ^0.19.0` or `^0.20.2`; `flutter_localizations` depends on one
  exact `intl`, so any app constraint that excludes it makes the whole app
  unresolvable the moment localization is added. `intl: any` defers to the SDK,
  which is the only thing that actually decides.
- **Adopting the library is step one of two.** It gives an app the twelve
  locales, the delegates and the shared vocabulary. It does not translate the
  app's own copy, and a store listing must not claim a language until that is
  done — see [`STORE_METADATA.md`](STORE_METADATA.md).
- **Count call sites, not ARB keys.** daily-pulse had 106 keys in nine
  languages and looked thoroughly localized. Only 6 of its 22 screens read a
  single one of them, and the onboarding screen — the first thing anyone sees —
  read none, so it opened in English no matter what the phone was set to.
  `grep -c "l10n\.\|AppLocalizations" <each screen>` before believing an app is
  translated.
- **Translating a screen finds its layout bugs.** Localizing daily-pulse's
  onboarding surfaced two overflows immediately: a column with no scroll, and a
  text column that was not `Expanded` — the Russian subtitle ran 77px past the
  row. Neither showed in English. Screenshot at least one long language (Russian
  or German) and run a 320dp widget test after localizing a screen.
- **`MaterialApp.locale` must be null to follow the device.** Several apps
  initialise their locale state to `Locale('en')`, which pins the app to
  English and makes the device's language irrelevant. Start at null and only
  set it when the user picks.
- **Do not hand-roll a `Directionality` wrapper.** `GlobalWidgetsLocalizations`
  already gives the resolved locale its own direction. A wrapper computed from
  app state overrides that, one frame behind.
- **In tests, set `localesTestValue`, not `localeTestValue`.** `WidgetsApp`
  resolves against `platformDispatcher.locales`; setting only the singular
  leaves the test running in English and passing for the wrong reason.
- **Do not invent a different word to satisfy the repeated-English check.**
  French really does say "Scanner", Italian says "Password", German says
  "Version". Add the pair to that app's per-locale exemption list instead.
